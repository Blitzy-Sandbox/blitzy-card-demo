# CardDemo Migration — Decision Log

This decision log is the single source of truth for every non-trivial decision made while migrating the AWS CardDemo application from COBOL / CICS / JCL to Java 25 LTS + Spring Boot 3.5.11. Each entry records the **decision**, the **alternatives considered**, the **rationale**, and the residual **risks**; per the user-specified *Explainability* rule this rationale lives here and is **never** duplicated in code comments, and any deviation from a literal COBOL interpretation is captured as an explicit row below. The COBOL baseline against which 100% behavioral parity is measured is the frozen legacy corpus at commit SHA `27d6c6f` — never the current `HEAD` of this repository.

| # | Decision | Alternatives Considered | Rationale | Risks |
|---|---|---|---|---|
| D-001 | Use `java.math.BigDecimal` (scale 2) for all COMP-3 / COMP monetary fields | `double` / `float`; `long` fixed-point cents | COBOL `PIC` clauses define exact decimal precision; `BigDecimal` with `compareTo` (not `equals`) reproduces `COMPUTE` / `ROUNDED` semantics identically and forbids any floating-point drift | Performance overhead vs. primitives, mitigated by confining `BigDecimal` strictly to monetary fields originating from a PIC decimal clause |
| D-002 | BCrypt password hashing for `USRSEC` users | Plaintext (preserve COBOL), Argon2, PBKDF2 | COBOL stores plaintext passwords; constraint C-003 explicitly permits the security upgrade while preserving the sign-on flow and login semantics | Existing plaintext credentials must be migrated via a hash-on-first-login pattern; legacy originals cannot be auto-rehashed without a known cleartext |
| D-003 | S3 versioned objects to replace GDG generation datasets | Local filesystem with rotation, PostgreSQL LOB columns | GDG semantics require generation numbering and retention; S3 object versioning across the three buckets (`carddemo-batch-input` / `-output` / `-statements`) is the native generation/retention equivalent | Requires LocalStack for local and integration testing; S3 versioning incurs storage cost |
| D-004 | SQS FIFO to replace the CICS Transient Data Queue `JOBS` | In-memory queue, Apache Kafka, RabbitMQ | CICS TDQ is point-to-point with strict sequential read; the SQS FIFO queue `carddemo-report-jobs.fifo` preserves identical ordering and submit-then-process semantics for the report bridge (F-011) | SQS FIFO has a 300 msg/sec throughput ceiling, which is sufficient for this workload |
| D-005 | Spring Batch for the JCL batch pipeline | Custom scheduler, Quartz, Temporal | JCL jobs are sequential batch steps gated by condition codes; Spring Batch provides native Job / Step / Flow sequencing, restartability, parameters, and condition evaluation | Learning curve for the Step / Job / Flow abstractions |
| D-006 | Stateless JWT via Spring Security 6 `SecurityFilterChain`, replacing CICS pseudo-conversational COMMAREA state | Server-side `HttpSession`, sticky-session clustering, re-creating the COMMAREA in a distributed cache | CICS carries cross-screen state in the COMMAREA (`COCOM01Y`); externalizing it into signed JWT claims matches the navigation contract with no server-side session and enables horizontal scaling — re-creating mainframe server state is a Spring anti-pattern | Token revocation/expiry must be managed; the JWT signing secret must be externalized (hardcoded in config at authoring time — a known open risk) |
| D-007 | JPA `@Version` optimistic locking to reproduce the `9300-CHECK-CHANGE-IN-REC` re-read-and-compare guard | Pessimistic `SELECT … FOR UPDATE`, no concurrency guard, manual snapshot comparison in application code | `COACTUPC` and `COCRDUPC` re-read and compare the before/after record image before rewrite; `@Version` on `Account` and `Card` raises `OptimisticLockException`, surfacing the same "record changed by another user" outcome the COBOL produced | Callers must catch the lock exception and re-present current data; a version column is added to the affected tables |
| D-008 | `@Transactional(rollbackFor = Exception.class)` to map CICS `SYNCPOINT` and implicit batch commits | Manual JDBC commit/rollback, programmatic `TransactionTemplate`, JDBC autocommit | The sole `SYNCPOINT ROLLBACK` in `COACTUPC` (atomic dual `ACCTDAT` + `CUSTDAT` rewrite) and implicit batch commits become declarative atomic units of work that commit or roll back as one | Checked exceptions must be enrolled via `rollbackFor`; long transactions can hold locks, mitigated by chunk sizing in batch |
| D-009 | Typed exception hierarchy (7 classes) + `FileStatusMapper` + `@ControllerAdvice` `GlobalExceptionHandler` for VSAM `FILE STATUS` codes | Return-code sentinels, a single generic exception, HTTP status codes only | Every two-character FILE STATUS code maps to a specific exception (`00` success, `23` `RecordNotFoundException`, `35` `FileNotFoundException`, `22` `DuplicateKeyException`, `9x` logic errors) so downstream branch logic still keys off the same conditions; centralized advice yields consistent error responses | The mapping table must remain exhaustive; an unmapped status must fail loudly rather than be silently swallowed |
| D-010 | Flyway `V1__create_schema` / `V2__create_indexes` / `V3__seed_data` for the 11 VSAM datasets → 11 PostgreSQL tables | Hibernate `ddl-auto=update`, hand-run SQL scripts, Liquibase | Versioned, repeatable migrations preserve record layouts and keys (V1), express VSAM AIX/PATH as secondary indexes (V2), and seed from the 9 authoritative ASCII fixtures (V3), giving a clean-checkout bootstrap | Applied migrations are immutable and may only be superseded by new versions; seed inserts must match fixture offsets/lengths exactly |
| D-011 | DTO layer derived from the 17 BMS symbolic maps, decoupling the REST contract from JPA entities | Expose entities directly, generic `Map` / raw JSON, share one model across all layers | The BMS symbolic maps define byte-accurate field contracts (names, `PIC` lengths, validation attributes); the 9 DTOs preserve them exactly while letting persistence evolve independently and making bean-validation constraints explicit | Extra entity ↔ DTO mapping code; DTO field lengths and semantics must stay synchronized with the frozen maps |
| D-012 | `@EmbeddedId` composite-key classes for `TCATBALF`, `DISCGRP`, and `TRANCATG` | Surrogate auto-increment id, JPA `@IdClass`, a concatenated string key | These VSAM records are keyed by multi-field natural keys; `@EmbeddedId` preserves the exact composite-key fields and ordering the COBOL reads rely on | Composite keys are more verbose in queries; `equals` / `hashCode` on the key class must be correct and stable |
| D-013 | `RoundingMode.HALF_EVEN` for the interest formula `(TRAN-CAT-BAL × DIS-INT-RATE) / 1200`, evaluated without algebraic rearrangement | `HALF_UP`, `double` arithmetic, simplifying or reordering the expression | COBOL default rounding is banker's rounding; preserving operand order and HALF_EVEN reproduces the legacy result bit-for-bit for the Gate 1 / Gate 4 byte-equivalence comparison | Any reordering, scale change, or rounding-mode swap risks penny-level divergence; locked down by golden-file comparison |
| D-014 | Spring profiles `local` (LocalStack + local PostgreSQL) and `test` (Testcontainers); no `prod` profile authored | A single hardcoded configuration, environment-variable-only config, authoring a production profile now | Profiles satisfy the configurable-RDBMS requirement and cleanly isolate LocalStack vs. Testcontainers wiring; production deployment and a `prod` profile are explicitly out of scope at authoring time | Absence of a production profile is a known, deferred open risk; production secret management (including the JWT signing key) is deferred with it |
| D-015 | Micrometer + OpenTelemetry tracing, Logback JSON (`logstash-logback-encoder`) with correlation IDs, and Spring Boot Actuator as the observability baseline | No observability, plain text logs only, a proprietary third-party APM agent | The *Observability* rule requires structured logging with correlation IDs, distributed tracing across service boundaries, a metrics endpoint, and health/readiness checks shipped with the initial implementation and verifiable locally (Jaeger / Prometheus / Grafana in Docker Compose) | Added dependency and configuration surface; trace and metric cardinality must be controlled to bound overhead |
| D-016 | `BatchPipelineOrchestrator` using `JobExecutionDecider` for JCL `COND` logic and `FlowBuilder.split()` for parallel `CREASTMT` / `TRANREPT` | One linear job, external shell-script orchestration, manual in-code condition checks | JCL `COND` codes map to `ExitStatus` + `JobExecutionDecider` so a non-zero POSTTRAN code still permits eligible downstream steps; stages 4a/4b run concurrently after COMBTRAN, mirroring the legacy flow | Parallel steps need isolated writers and resources; the decider logic must mirror every legacy COND rule exactly |
| D-017 | Zero-warning build enforced with `-Xlint:all`, with a documented exception for framework-generated code | Default lenient compilation, ad-hoc `@SuppressWarnings`, full `-Werror` including generated sources | Gate 2 requires a clean-checkout deployable artifact with zero warnings; `-Xlint:all` surfaces all `javac` warnings, and framework-generated code is the single sanctioned exception | Strict linting can block builds on transitive or generated code; the exception scope must stay narrow and documented |
| D-018 | Map the conceptual `carddemo-java/` target repository onto THIS repository root (no nested sub-folder) | Create a nested `carddemo-java/` directory; stand up a separate physical repository | The blueprint's `carddemo-java/` is a conceptual root; placing `pom.xml`, `src/`, and the docs at the actual repo root keeps the Maven standard layout and tooling paths simple and matches the single-module greenfield intent — a deliberate deviation from the literal path, recorded here per the *Explainability* rule | Readers of the specification must mentally strip the `carddemo-java/` prefix; documented here to prevent path confusion |
