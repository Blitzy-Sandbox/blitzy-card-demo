# CardDemo Migration — Decision Log

This decision log is the single source of truth for every non-trivial decision made while migrating the AWS CardDemo application from COBOL / CICS / JCL to Java 25 LTS + Spring Boot 3.5.11. Each entry records the **decision**, the **alternatives considered**, the **rationale**, and the residual **risks**; per the user-specified *Explainability* rule this rationale lives here and is **never** duplicated in code comments, and any deviation from a literal COBOL interpretation is captured as an explicit row below. The COBOL baseline against which 100% behavioral parity is measured is the frozen legacy corpus at commit SHA `27d6c6f` — never the current `HEAD` of this repository.

| # | Decision | Alternatives Considered | Rationale | Risks |
|---|---|---|---|---|
| D-001 | Use `java.math.BigDecimal` (scale 2) for all COMP-3 / COMP monetary fields | `double` / `float`; `long` fixed-point cents | COBOL `PIC` clauses define exact decimal precision; `BigDecimal` with `compareTo` (not `equals`) reproduces `COMPUTE` / `ROUNDED` semantics identically and forbids any floating-point drift | Performance overhead vs. primitives, mitigated by confining `BigDecimal` strictly to monetary fields originating from a PIC decimal clause |
| D-002 | BCrypt password hashing for `USRSEC` users | Plaintext (preserve COBOL), Argon2, PBKDF2 | COBOL stores plaintext passwords; constraint C-003 explicitly permits the security upgrade while preserving the sign-on flow and login semantics | Existing plaintext credentials must be migrated via a hash-on-first-login pattern; legacy originals cannot be auto-rehashed without a known cleartext |
| D-003 | S3 versioned objects to replace GDG generation datasets | Local filesystem with rotation, PostgreSQL LOB columns | GDG semantics require generation numbering and retention; S3 object versioning across the three buckets (`carddemo-batch-input` / `-output` / `-statements`) is the native generation/retention equivalent | Requires LocalStack for local and integration testing; S3 versioning incurs storage cost |
| D-004 | SQS FIFO to replace the CICS Transient Data Queue `JOBS` | In-memory queue, Apache Kafka, RabbitMQ | CICS TDQ is point-to-point with strict sequential read; the SQS FIFO queue `carddemo-report-jobs.fifo` preserves identical ordering and submit-then-process semantics for the report bridge (F-011) | SQS FIFO has a 300 msg/sec throughput ceiling, which is sufficient for this workload |
| D-005 | Spring Batch for the JCL batch pipeline | Custom scheduler, Quartz, Temporal | JCL jobs are sequential batch steps gated by condition codes; Spring Batch provides native Job / Step / Flow sequencing, restartability, parameters, and condition evaluation | Learning curve for the Step / Job / Flow abstractions |
| D-006 | Stateless JWT via Spring Security 6 `SecurityFilterChain`, replacing CICS pseudo-conversational COMMAREA state | Server-side `HttpSession`, sticky-session clustering, re-creating the COMMAREA in a distributed cache | CICS carries cross-screen state in the COMMAREA (`COCOM01Y`); externalizing it into signed JWT claims matches the navigation contract with no server-side session and enables horizontal scaling — re-creating mainframe server state is a Spring anti-pattern | Token revocation/expiry must be managed; the JWT signing secret must be externalized (hardcoded in config at authoring time — a known open risk) |
| D-007 | JPA `@Version` optimistic locking to reproduce the `9300-CHECK-CHANGE-IN-REC` re-read-and-compare guard | Pessimistic `SELECT … FOR UPDATE`, no concurrency guard, manual snapshot comparison in application code | `COACTUPC` and `COCRDUPC` re-read and compare the before/after record image before rewrite; `@Version` on `Account` and `Card` raises `OptimisticLockException`, surfacing the same "record changed by another user" outcome the COBOL produced | Callers must catch the lock exception and re-present current data; a version column is added to the affected tables |
| D-008 | `@Transactional(rollbackFor = Exception.class)` to map CICS `SYNCPOINT` and implicit batch commits | Manual JDBC commit/rollback, programmatic `TransactionTemplate`, JDBC autocommit | The sole `SYNCPOINT ROLLBACK` in `COACTUPC` (atomic dual `ACCTDAT` + `CUSTDAT` rewrite) and implicit batch commits become declarative atomic units of work that commit or roll back as one | Checked exceptions must be enrolled via `rollbackFor`; long transactions can hold locks, mitigated by chunk sizing in batch |
| D-009 | Typed exception hierarchy (7 classes) + `FileStatusMapper` + `@ControllerAdvice` `GlobalExceptionHandler` for VSAM `FILE STATUS` codes | Return-code sentinels, a single generic exception, HTTP status codes only | Every two-character FILE STATUS code maps to a specific exception (`00` success, `23` `RecordNotFoundException`, `35` `FileNotFoundException`, `22` `DuplicateKeyException`, `9x` logic errors) so downstream branch logic still keys off the same conditions; centralized advice yields consistent error responses | The mapping table must remain exhaustive; an unmapped status must fail loudly rather than be silently swallowed |
| D-010 | Flyway `V1__create_schema` / `V2__create_indexes` / `V3__seed_data` for the 11 VSAM datasets → 11 PostgreSQL tables | Hibernate `ddl-auto=update`, hand-run SQL scripts, Liquibase | Versioned, repeatable migrations preserve record layouts and keys (V1), express VSAM AIX/PATH as secondary indexes (V2), and seed from the 9 authoritative ASCII fixtures (V3), giving a clean-checkout bootstrap | Applied migrations are immutable and may only be superseded by new versions; seed inserts must match fixture offsets/lengths exactly |
| D-011 | DTO layer derived from the 17 BMS symbolic maps, decoupling the REST contract from JPA entities | Expose entities directly, generic `Map` / raw JSON, share one model across all layers | The BMS symbolic maps define byte-accurate field contracts (names, `PIC` lengths, validation attributes); the 9 DTOs preserve them exactly while letting persistence evolve independently and making bean-validation constraints explicit | Extra entity ↔ DTO mapping code; DTO field lengths and semantics must stay synchronized with the frozen maps |
| D-012 | `@EmbeddedId` composite-key classes for `TCATBALF`, `DISCGRP`, and `TRANCATG` | Surrogate auto-increment id, JPA `@IdClass`, a concatenated string key | These VSAM records are keyed by multi-field natural keys; `@EmbeddedId` preserves the exact composite-key fields and ordering the COBOL reads rely on | Composite keys are more verbose in queries; `equals` / `hashCode` on the key class must be correct and stable |
| D-013 | `RoundingMode.HALF_EVEN` for the interest formula `(TRAN-CAT-BAL × DIS-INT-RATE) / 1200`, evaluated without algebraic rearrangement | `HALF_UP`, `double` arithmetic, simplifying or reordering the expression | COBOL default rounding is banker's rounding; preserving operand order and HALF_EVEN reproduces the legacy result bit-for-bit for the Gate 1 / Gate 4 byte-equivalence comparison | Any reordering, scale change, or rounding-mode swap risks penny-level divergence; locked down by golden-file comparison |
| D-014 | Spring profiles `local` (LocalStack + local PostgreSQL) and `test` (Testcontainers); no `prod` profile authored | A single hardcoded configuration, environment-variable-only config, authoring a production profile now | Profiles satisfy the configurable-RDBMS requirement and cleanly isolate LocalStack vs. Testcontainers wiring; production deployment and a `prod` profile are explicitly out of scope at authoring time | Absence of a production profile is a known, deferred open risk; production secret management (including the JWT signing key) is deferred with it |
| D-015 | Micrometer + OpenTelemetry tracing, Logback JSON (`logstash-logback-encoder`) with correlation IDs, and Spring Boot Actuator as the observability baseline | No observability, plain text logs only, a proprietary third-party APM agent | The *Observability* rule requires structured logging with correlation IDs, distributed tracing across service boundaries, a metrics endpoint, and health/readiness checks shipped with the initial implementation and verifiable locally (Jaeger / Prometheus / Grafana in Docker Compose) | Added dependency and configuration surface; trace and metric cardinality must be controlled to bound overhead |
| D-016 | `BatchPipelineOrchestrator` using `JobExecutionDecider` for JCL `COND` logic and `FlowBuilder.split()` for parallel `CREASTMT` / `TRANREPT` | One linear job, external shell-script orchestration, manual in-code condition checks | JCL `COND` codes map to `ExitStatus` + `JobExecutionDecider` so a non-zero POSTTRAN code still permits eligible downstream steps; stages 4a/4b run concurrently after COMBTRAN, mirroring the legacy flow | Parallel steps need isolated writers and resources; the decider logic must mirror every legacy COND rule exactly |
| D-017 | Zero-warning build enforced with `-Xlint:all`, with a documented exception for framework-generated code | Default lenient compilation, ad-hoc `@SuppressWarnings`, full `-Werror` including generated sources | Gate 2 requires a clean-checkout deployable artifact with zero warnings; `-Xlint:all` surfaces all `javac` warnings, and framework-generated code is the single sanctioned exception | Strict linting can block builds on transitive or generated code; the exception scope must stay narrow and documented |
| D-018 | Map the conceptual `carddemo-java/` target repository onto THIS repository root (no nested sub-folder) | Create a nested `carddemo-java/` directory; stand up a separate physical repository | The blueprint's `carddemo-java/` is a conceptual root; placing `pom.xml`, `src/`, and the docs at the actual repo root keeps the Maven standard layout and tooling paths simple and matches the single-module greenfield intent — a deliberate deviation from the literal path, recorded here per the *Explainability* rule | Readers of the specification must mentally strip the `carddemo-java/` prefix; documented here to prevent path confusion |
| D-019 | Restrict account phone area-code validation to the COBOL general-purpose code set only (`validGeneralPurposeCodes`), excluding easy-recognizable / special codes | Keep the precomputed `validPhoneAreaCodes` union array; merge every JSON array generically; validate against the full NANPA list | `COACTUPC` phone validation uses `IF VALID-GENERAL-PURP-CODE` only, so codes such as 200 / 211 / 911 / 900 must be rejected. `ValidationLookupService.load()` now reads exactly the `validGeneralPurposeCodes` property (fail-fast if absent), and the over-permissive union array was removed from `nanpa-area-codes.json`, restoring byte-for-byte validation parity | The two NANPA arrays must stay partitioned; a future loader change that re-merges them would silently re-introduce over-permissive validation. Guarded by `ValidationLookupServiceTest` (accepts 201 / 212, rejects 200 / 211 / 911 / 900) |
| D-020 | Treat the JWT signing secret as Base64-encoded random key material, Base64-decoded before `Keys.hmacShaKeyFor` | Use raw `secret.getBytes(UTF_8)` directly; inject a pre-provisioned `SecretKey` bean; generate a key at startup | Raw UTF-8 bytes make the configured key interpretation ambiguous and conflict with JJWT's recommended encoded-secret handling. Decoding a Base64 key yields unambiguous, high-entropy material and still fails fast on weak keys. The required format is documented in `application.yml`, `application-local.yml`, and the `JwtTokenService` constructor Javadoc | Operators must supply a Base64 string whose decoded length is at least 32 bytes (256 bits); a non-Base64 or too-short value fails at startup by design |
| D-021 | Remove the hardcoded `:carddemo` datasource-password fallback from the profile-agnostic `application.yml`; isolate the local-development default in the local-only `application-local.yml` | Keep the base fallback; require `POSTGRES_PASSWORD` everywhere with no local default; document the password only in onboarding text | The base file loads for every profile, so a base fallback is an effective hardcoded credential (CWE-798). The base now requires `POSTGRES_PASSWORD` (fail-fast when absent), while the explicitly non-production `local` profile keeps a convenience default so a clean machine still runs (R3 onboarding) | Non-local deployments MUST inject `POSTGRES_PASSWORD`; the local-only default must never be promoted to a deployed environment |
| D-022 | Remove the `toString()` methods from the `Account`, `CardXref`, and `DailyTransaction` entities | Mask / redact selected fields; keep `toString()` but exclude sensitive fields; rely on logging configuration to filter | Those `toString()` methods rendered balances, credit limits, full card numbers (PAN), transaction amounts, and merchant data, risking sensitive financial / PII exposure through logs or exception messages (CWE-532). Removing them eliminates the implicit leak path while identifier-based `equals` / `hashCode` are retained | Diagnostic logs no longer auto-render these entities; any future `toString()` on a sensitive entity must redact the sensitive fields |
| D-023 | Retain the `javax.sql.DataSource` (`HealthIndicators`) and `javax.crypto.SecretKey` (`JwtTokenService`) imports as Java SE / JDK APIs | Mechanically replace every `javax.*` token to satisfy a literal text check; wrap the JDK types to hide the package | The Jakarta EE 10 baseline (AAP §3.3) bans only the Java EE `javax.*` packages renamed to `jakarta.*` (persistence, validation, servlet). `javax.sql` and `javax.crypto` are JDK Java SE packages with no `jakarta.*` equivalent and must remain `javax.*`; the migration uses `jakarta.persistence` / `jakarta.validation` correctly elsewhere | A purely textual `javax.*` lint must whitelist JDK Java SE packages (`javax.sql`, `javax.crypto`, etc.) to avoid false positives |
| D-024 | Bind OWASP dependency-check to the `verify` phase (goal `check`, `failBuildOnCVSS=7`), drop `-processing` from the compiler `-Xlint` args, and add `.mvn/jvm.config` toolchain flags | Leave dependency-check on-demand only; keep `-Xlint:all,-processing`; pass toolchain flags through `MAVEN_OPTS` only | Gate 8 requires the zero-critical / high-CVE check to run on `mvn verify`, not only on demand. `-Xlint:all` without `-processing` restores full warning coverage for handwritten code under `-Werror`. `.mvn/jvm.config` (`--enable-native-access=ALL-UNNAMED`, `--sun-misc-unsafe-memory-access=allow`) silences cosmetic JDK 25 runtime noise for a clean-checkout build independent of environment variables | `verify` now performs an NVD-backed scan (network or cached data needed); the jvm.config flags are JDK 25-specific and should be revisited on a JDK upgrade |
| D-025 | Register `carddemo.transaction.amount.total` as a Micrometer `DistributionSummary`, replace the single untagged rejected counter with a per-`RejectReasonCode` tagged counter map, and align the Grafana dashboard PromQL | Keep the amount metric as a `Counter`; keep one untagged rejected counter and change only the dashboard; rename the meter | The dashboard queries distribution series (`_sum` / `_count`) and `sum by (reason)`. A `DistributionSummary` emits `_sum` / `_count`, and reason-tagged counters emit the `reason` label. Micrometer strips the reserved `_total` suffix from non-counter meters, so the dashboard amount panels were updated to `carddemo_transaction_amount_sum` / `_count`. The meter NAME `carddemo.transaction.amount.total` is preserved because the tech-spec names it as the contract | Renaming the meter later would break both the dashboard and the documented contract; `baseUnit` must be omitted on these meters to avoid a unit suffix being injected into the series name |
| D-026 | Seed `daily_transaction` in `V3__seed_data.sql` from the 9th ASCII fixture `dailytran.txt` (300 records, CVTRA06Y offsets, COBOL zoned-overpunch sign decode); keep the posted `transactions` table empty; map the staging entity with a raw `String` type code, no `@Version`, `CHAR` JDBC binding, and no FILLER column | Leave `daily_transaction` empty; load the fixture at runtime; model the staging type code as an enum; add a version column; also seed `transactions` | CP1 / AAP requires V3 to seed all 9 fixtures so the primary posting pipeline (`CBTRN02C`) has authoritative input at clean checkout. `transactions` has no fixture and is populated by posting, so it stays empty by design. Staging rows are unvalidated batch input that must load without throwing, so `tran_type_cd` stays a raw `CHAR(2)` String validated downstream by the four-stage cascade; staging needs no optimistic locking (no `@Version`); `@JdbcTypeCode(CHAR)` keeps `ddl-auto=validate` parity with the Flyway `CHAR` columns; the trailing `FILLER PIC X(20)` carries no data and is unmapped | Seed inserts must match fixture offsets / lengths and overpunch sign decoding exactly (golden-file verified: 300 rows; amounts include 504.77 and -919.00); any copybook offset drift would corrupt the staging input |
| D-027 | Move the structured-logging design rationale out of `logback-spring.xml` XML comments into this log, leaving only operational / factual comments in the file | Keep the rationale inline in the XML comments; remove the comments entirely | R4 / Explainability requires design rationale to live in `DECISION_LOG.md`, not code or config comments. The file retains only operational facts (MDC key producers, the JSON-vs-plain output contract, and the framework requirement that the file be named `logback-spring.xml` for the Spring extension elements). The rationale: the profile split keeps machine-parseable JSON in non-local environments while giving local developers readable colored output; the field names `correlationId` / `traceId` / `spanId` match the dashboard and trace backend; MDC emission is restricted to those keys to bound log cardinality and avoid leaking arbitrary context | Maintainers must consult this log for the why; the operational notes left in the file must be kept accurate |
| D-028 | Upgrade the JaCoCo Maven plugin from 0.8.12 to 0.8.14 | Stay on 0.8.12; disable coverage instrumentation; switch coverage tooling | JaCoCo 0.8.12 throws `IllegalClassFormatException` while instrumenting Java 25 (class-file major version 69) bytecode, breaking `mvn test`. 0.8.14 adds Java 25 class-file support, restoring the Gate 8 coverage gate. Consistent with the AAP §0.5.1 JaCoCo coordinate, which pins the plugin without freezing a sub-minor incompatible with the chosen JDK | Coverage thresholds are unchanged; a future JDK may again require a JaCoCo bump |
| D-029 | Add `@JdbcTypeCode(SqlTypes.CHAR)` to `User.userId` (`CHAR(8)` primary key) and `User.userType` (`CHAR(1)`), and add a Testcontainers PostgreSQL 16 `RepositoryPersistenceIT` that boots under `ddl-auto=validate` | Leave `User` unbound (the latent state); rely on compile + unit tests only (the reviewed gap); switch `ddl-auto` to `none`/`update` to mask the mismatch | A real-database schema-validation IT — added to close the CP2 review's repository / schema test-coverage gap — surfaced that `users.user_id` / `user_type` were the only fixed-width `CHAR` columns mapped without the JDBC `CHAR` binding present on every other entity, so Hibernate `validate` expected `VARCHAR` and the application context failed to start against PostgreSQL `bpchar`. Applying the established binding (same pattern as D-012 / D-026 and the `DisclosureGroupId` correction) restores `ddl-auto=validate` parity and Gate 2 deployability; masking it via `ddl-auto` would hide a genuine record-layout-fidelity defect (§0.6.4) | Any future fixed-width `CHAR` column added without the binding will again break startup; now guarded by `RepositoryPersistenceIT`, which validates the full schema for all mapped entities and exercises derived-query parsing and the `DisclosureGroup` composite-key round-trip against a live database |
| D-030 | `config/ObservabilityConfig` contributes only the non-auto-configured observability glue — a distribution-statistics `MeterFilter` (percentile histograms + p50/p95/p99 for `http.server.requests` and `carddemo.*` meters) plus the `ObservedAspect` / `TimedAspect` aspects that activate `@Observed` / `@Timed` across service boundaries — and adds NO `spring-boot-starter-aop` dependency | Add `spring-boot-starter-aop` explicitly; omit the aspects and ship only the histogram filter; configure HTTP histograms via `management.metrics.distribution` properties in `application.yml`; register a second `MeterRegistry` or common tags in this class | The Observability rule requires distributed tracing across service boundaries, and `@Observed` / `@Timed` provide per-operation spans and timers idiomatically. AspectJ auto-proxying is already active because `aspectjweaver` (transitively via `spring-aspects` from `spring-boot-starter-data-jpa`) and `spring-aop` (via `spring-boot-starter-security`) are on the classpath, so Spring Boot `AopAutoConfiguration` enables proxying without `spring-boot-starter-aop` — which is additionally absent from the offline Maven cache and would break the clean zero-warning build. The `MeterFilter` yields dashboard-ready latency distributions without re-adding the common `application` tag (owned by `application.yml`) or re-declaring the four `carddemo.*` meters (owned by `observability/MetricsConfig`); correlation-ID / MDC remains owned by `observability/CorrelationIdFilter`, so this class imports no `com.carddemo.*` type and references no endpoint or secret (trace export, sampling, and Prometheus export stay property-driven) | Aspect proxying depends on `aspectjweaver` / `spring-aop` remaining transitively present; a future dependency prune would silently disable the annotations, mitigated because both are first-class transitive dependencies of starters already in use. Percentile histograms add metric cardinality, bounded by scoping the filter to HTTP and `carddemo.*` meters only |
| D-031 | `config/AwsConfig` externalizes the AWS resource names (the three S3 buckets, the SQS FIFO report queue, and the SNS topic) into a single validated `@ConfigurationProperties(prefix = "carddemo.aws")` holder (`AwsResourceProperties`) and relies on Spring Cloud AWS 3.3.0 auto-configuration for the `S3Client` / `SqsAsyncClient` / `SnsClient` (and `S3Template` / `SqsTemplate` / `SnsTemplate`) — it declares NO client beans | Define explicit client `@Bean`s with the endpoint set in code; hardcode the bucket / queue / topic names at each call site; scatter `@Value("${carddemo.aws...}")` injections across consumers; use immutable `@ConstructorBinding` records | The `spring-cloud-aws-starter-s3/-sqs/-sns` starters auto-configure the clients and templates from the `spring.cloud.aws.*` properties, so the LocalStack endpoint + S3 path-style overrides in the `local` / `test` profiles drive every client uniformly (LocalStack Verification rule); declaring a client bean here would conflict (`NoUniqueBeanDefinitionException`) and bypass the property-driven endpoint that `observability/HealthIndicators` and the Testcontainers suites depend on. A single typed bean is the one source of truth for the names — kept identical to `application.yml` and `localstack-init/init-aws.sh` (S3 `carddemo-batch-input` / `-output` / `carddemo-statements`, SQS `carddemo-report-jobs.fifo`, SNS `carddemo-notifications`) — and never hardcodes any name, endpoint, region, or credential in code; `@Validated` + `@NotBlank` (cascaded via `@Valid`) fail fast on a blank name at startup | The names must stay synchronized across `application.yml`, `init-aws.sh`, and the Testcontainers provisioning; a future explicit client bean would silently override auto-config — guarded by the `s3` / `sqs` Actuator health indicators and the LocalStack integration tests |
