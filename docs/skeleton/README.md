# CardDemo Modernized Walking Skeleton

This documentation set describes the **CardDemo modernized walking skeleton** — a **structural / topology run** whose success is defined by the seams holding together, not by behavioral parity with the legacy application. The skeleton **builds green** and runs exactly **one** live vertical tracer slice (Card Detail) end-to-end — an authenticated request flowing UI → BFF → `card-svc` → Oracle `FREEPDB1` (a seeded row) → a rendered Card Detail screen with real loading, empty, and error states — while all remaining business logic is deliberately **stubbed as typed placeholders**. The governing intent rule is that **a stub returning a typed placeholder is the correct outcome; a hallucinated (invented) implementation is a failure.** The single live tracer is sourced from the legacy Credit Card View path `[SRC: COCRDSLC | CARDDAT]`.

## Pinned Target Stack

- **Java 21 + Spring Boot 3.5.x** (latest 3.x patch line), one deployable service per bounded context `[SRC: CARDDEMO.CSD]`.
- **Oracle Database 23ai** via `gvenzl/oracle-free` (PDB **`FREEPDB1`**, port 1521, an explicit pinned image tag — never `latest`); JDBC driver **`ojdbc11`** (23.26.2.0.0).
- **JPA / Hibernate `OracleDialect` + Flyway** migrations; surrogate primary keys via `GENERATED BY DEFAULT AS IDENTITY` (seed-safe); the `CARD` table is keyed on the natural `CARD_NUM` `[SRC: CVACT02Y | CARDDAT]`.
- **OpenAPI 3.1** contract-first codegen — a frozen single source of truth under `/contracts/**`; generator `openapi-generator-maven-plugin` 7.23.0 (`spring`, `interfaceOnly`) for the Java servers and `typescript-axios` for the UI client.
- **React 19 + TypeScript + Vite + MUI v9** SPA (`@mui/material` 9.0.1 core + Emotion) that binds **only** to the thin **BFF**.
- **docker-compose** as the single-VM deployment unit (**no Kubernetes, no serverless**); startup gated by `depends_on: condition: service_healthy` (Oracle → Flyway → request-serving services; `reporting-svc` exempt).

## Supersession Note

For the **skeleton run**, the run contract is authoritative, and **this `docs/skeleton/**` set is the authoritative documentation** — it **supersedes `docs/technical-specifications.md`** (and the other superseded sibling docs) for the skeleton run. The rationale follows the AAP §0.1.2 conflict-resolution note: the pre-existing technical specification describes a materially different, superseded target — **Java 25 / Spring Boot 3.5.x on PostgreSQL 16** with **AWS S3/SQS/SNS (via LocalStack)**, **Spring Batch**, a **Micrometer / Jaeger / Prometheus / Grafana** observability stack, and a **REST-only** backend with the browser UI explicitly excluded — whereas the run contract pins **Java 21 / Spring Boot 3 on Oracle 23ai**, a **React 19 + MUI SPA + BFF** UI tier, **OpenAPI-generated** clients, and a **docker-compose single-VM** deploy. The three sibling files (`docs/index.md`, `docs/project-guide.md`, `docs/technical-specifications.md`) remain **unchanged**; they are simply **not authoritative** for the skeleton.
