# Decision Log

This Decision Log is the single source of truth for **why** each non-trivial choice was made while migrating the AWS CardDemo application from its legacy COBOL / CICS / VSAM / JCL mainframe stack to **Java 25 LTS + Spring Boot 3.5.11**. It fulfils the migration's **Explainability** requirement: architectural and design rationale lives here — in documentation — and never in code comments.

> **Source of truth.** The legacy COBOL programs, copybooks, and JCL jobs are the authoritative behavioral baseline for this migration. They are **not copied into this repository**; instead they are referenced by their original commit SHA **`27d6c6f`** (full `7756d895ffeb65f7ea72aaa609e356d9899afcec`). Every decision below preserves the behavior observed in that frozen source unless it is explicitly flagged as a logged deviation.

Each row records a decision, the alternatives that were weighed, the rationale for the choice, and the residual risk (with its mitigation). IDs are stable and sequential (`D-001`, `D-002`, …) so they can be cited from the [Traceability Matrix](traceability-matrix.md), the [Project Guide](project-guide.md), and code reviews. Decisions `D-001`–`D-005` are carried forward from the seed set in the [Technical Specifications](technical-specifications.md) (§0.7.3); the remainder derive from the migration's refactoring rules and the open-risk register.

| ID | Decision | Alternatives Considered | Rationale | Risk |
|----|----------|-------------------------|-----------|------|
| D-001 | Use `java.math.BigDecimal` for every `COMP-3` / `COMP` / `PIC S9(n)V99` financial field | `double`; `long` scaled fixed-point; scaled `BigInteger` | COBOL PIC clauses define exact decimal precision and scale; `BigDecimal` with a matching scale plus an explicit `RoundingMode.HALF_UP` applied via `setScale(...)` reproduces COBOL arithmetic identically. Zero `float`/`double` for money (Goal G2). | Boxing/allocation overhead vs. primitives — mitigated by confining `BigDecimal` strictly to monetary fields. |
| D-002 | Hash user passwords with **BCrypt** (explicitly logged security **deviation**) | Preserve plaintext (literal COBOL parity); Argon2; PBKDF2; SHA-256 | COBOL `USRSEC` stores plaintext passwords (constraint C-003). BCrypt is a well-vetted adaptive default that keeps the sign-on flow semantics intact and satisfies the "no hardcoded credentials" rule; deviating from literal parity here is a deliberate security improvement. | Existing seed passwords must be migrated via hash-on-first-login or a re-seed with pre-hashed values; minor per-login CPU cost from the BCrypt work factor. |
| D-003 | Store GDG generations as **versioned Amazon S3 objects** | Local filesystem with generation rotation; PostgreSQL large objects (LOB); EFS | GDG generation numbering and retention map natively onto S3 object versioning; batch staging uses buckets `carddemo-batch-input`, `carddemo-batch-output`, and `carddemo-statements`. | Requires LocalStack for local/test runs; S3 versioning storage cost — mitigated by lifecycle rules. |
| D-004 | Use an **SQS FIFO** queue for the CICS Transient Data Queue (TDQ) report bridge | In-memory queue; Apache Kafka; RabbitMQ; a database polling table | A CICS TDQ is point-to-point with strictly sequential reads; SQS FIFO (`carddemo-report-jobs.fifo`) preserves ordering exactly. CORPT00C's TDQ→JES bridge becomes an SQS-triggered Spring Batch launch. | SQS FIFO caps at ~300 messages/sec — comfortably sufficient for this reporting workload. |
| D-005 | Re-platform the JCL pipeline on **Spring Batch** | Custom scheduler; Quartz; Temporal; shell + cron | JCL `EXEC PGM` + `DD` + `COND` map natively to Spring Batch Job/Step beans plus `JobExecutionDecider` and `FlowBuilder`; chunk-oriented steps replace `PERFORM UNTIL END-OF-FILE` read loops. | Team learning curve for the Step/Job/Flow abstractions — mitigated by the onboarding guide. |
| D-006 | Persist VSAM KSDS data in **PostgreSQL 16 via Spring Data JPA** | MongoDB; DynamoDB; flat files; H2 | VSAM KSDS keyed access maps to `@Entity` + `JpaRepository`; AIX/PATH alternate indexes become derived queries or `@Query`; `NUMERIC(p,s)` columns preserve decimal precision and scale. | ORM impedance vs. raw VSAM performance — mitigated by the V2 index migration. |
| D-007 | Use **JPA `@Version` optimistic locking** on `Account` and `Card` | Pessimistic DB locks; no locking; application-level field compare | COACTUPC (CAUP) and COCRDUPC (CCUP) perform read-then-rewrite with change detection; `@Version` reproduces this, and an `OptimisticLockException` maps to a 409-style typed error preserving the COBOL "record changed" behavior. | Version conflicts surface as HTTP 409 — clients must retry the read-modify-write cycle. |
| D-008 | Reproduce `EXEC CICS SYNCPOINT ROLLBACK` with **`@Transactional(rollbackFor=...)`** | Manual JDBC transactions; programmatic `TransactionTemplate` | The `SYNCPOINT ROLLBACK` in COACTUPC becomes declarative rollback at the service boundary, preserving all-or-nothing multi-table semantics. | Requires correct exception typing so the declared `rollbackFor` classes actually trigger rollback. |
| D-009 | Replace CICS pseudo-conversational COMMAREA state with **stateless REST + JWT** | Server-side HTTP session; sticky sessions; a Redis session store | `RETURN TRANSID COMMAREA` cross-screen state becomes a stateless JWT bearer token, allowing horizontal scaling with no server affinity. | The JWT signing secret is externalized to `${JWT_SECRET}` (fail-fast, no default) in base and prod configuration; the residual is provisioning it from a secrets manager / vault at deploy time (see the [Project Guide](project-guide.md)). Token size vs. the compact COMMAREA. |
| D-010 | Consolidate the 17 BMS screens into **8 REST controllers** | 1:1 screen→controller (17 controllers); GraphQL; server-rendered MVC | Screens are grouped by domain — Auth, Menu, Account, Card, Transaction, User, Report, BillPayment — into cohesive JSON APIs; the target is headless (no browser UI). | The screen→endpoint mapping must be tracked precisely — captured in the [Traceability Matrix](traceability-matrix.md). |
| D-011 | Manage the schema with **Flyway migrations** (V1 schema, V2 indexes, V3 seed) | Hibernate `ddl-auto`; Liquibase; hand-run SQL | Deterministic, versioned, repeatable schema derived from the copybook record layouts and `LISTCAT`; V3 seeds from the `app/data/ASCII` fixtures. | Migration-ordering discipline is required — documented as an onboarding pitfall. |
| D-012 | Implement DFSORT/MERGE keys as **`java.util.Comparator`** chains | An external sort utility; relying on DB `ORDER BY` alone | COMBTRAN DFSORT keys become `Comparator` implementations that preserve key order, direction (ascending/descending), and duplicate handling identically. | Comparator correctness must be verified against the original sort control cards. |
| D-013 | Map `FILE STATUS` handling to **7 typed exceptions plus status enums** | Numeric return codes; a generic `Exception`; `Optional`-only signaling | Each `FILE STATUS` inspection becomes a typed exception plus a status-enum `switch`; EOF (`'10'`) is treated as normal reader termination (`Optional.empty()`/null), NOT an exception; ABEND paragraphs become runtime exceptions with structured logging. | An exhaustive status-code-to-exception mapping is required for full parity. |
| D-014 | Replace LE `CEEDAYS` date validation with **`java.time.LocalDate` + custom validators** | A legacy date library; `String` dates; `java.util.Date` | CSUTLDTC's `CEEDAYS` validation becomes `LocalDate` plus Jakarta validators, alongside NANPA phone, US state/ZIP, and FICO-range validators. | Edge-case date rules (era/Lilian boundaries) must match `CEEDAYS` exactly. |
| D-015 | Replace inter-program `CALL` linkage with **constructor dependency injection** | Static utility calls; a service locator; field injection | CBSTM03A's `CALL 'CBSTM03B'` becomes a constructor-injected `StatementFileService` bean; `USING`/`RETURNING` linkage becomes method parameters and return values. | Standard Spring idiom — no significant residual risk. |
| D-016 | **Remain on Spring Boot 3.x (pinned to 3.5.11)** — a deliberate currency decision (**deviation**) | Upgrade to Spring Boot 4.0/4.1 (on Spring Framework 7) | The explicit user mandate is "Spring Boot 3.x". As of this migration the Spring Boot 3.5 line reached **OSS end-of-life on 2026-06-30** (final OSS patch 3.5.16); the 3.x→4.x upgrade is deferred to a logged suggested next task in the Onboarding Guide (`onboarding.md`, forthcoming). | **Currency risk** — running on an EOL minor. Remediate by first moving to 3.5.16, then planning the 3.x→4.x migration. |
| D-017 | Use **Spring Cloud AWS 3.3.0** on AWS SDK v2 for S3/SQS/SNS | AWS SDK v2 used directly; the newer 3.4.x line; Spring Cloud AWS 2.x | 3.3.0 (released January 2025) provides S3/SQS/SNS auto-configuration and first-class LocalStack support on AWS SDK v2. | A 3.4.x line exists and is noted as an upgrade consideration. |
| D-018 | Use **Testcontainers 2.0.3 + the LocalStack module**, with tests self-provisioning AWS resources | Mocked AWS SDK; a shared long-lived LocalStack instance; embedded fakes | The LocalStack Verification rule mandates zero live AWS; integration tests create their own S3 buckets and SQS queues in `@BeforeAll` and delete them in `@AfterAll`, never depending on pre-existing state. | Docker must be available in CI and developer environments — documented as an onboarding pitfall. |
| D-019 | Drive the migration and database seeding from the **9 ASCII fixtures** under `app/data/ASCII/` | Use the EBCDIC fixtures directly; synthesize fresh test data | The ASCII fixtures are the named validation artifacts for Gates 1 and 4 and seed the target database; the 13 EBCDIC files are reference-only, avoiding an EBCDIC→ASCII code-page conversion in the primary path. | A production EBCDIC data-migration strategy is deferred — tracked in the open-risk register. |
| D-020 | Deliver a **headless REST-only** backend with no UI and no design system | A single-page application; server-rendered pages; a component/design-system UI | The 3270 BMS screens become JSON REST endpoints; per the UI applicability assessment (§7.1) there is no browser UI, so Design System Compliance is not applicable. | Any future UI is out of scope for this migration and must be planned separately. |
| D-021 | Ship **observability from day one** — structured logging, tracing, metrics, and health | Add observability as a post-migration follow-up; logs only | The legacy system had zero observability; the target emits JSON logs (`logstash-logback-encoder` 8.0) with an MDC `correlationId`, distributed traces via Micrometer Tracing→OpenTelemetry→Jaeger, Prometheus metrics at `/actuator/prometheus`, health/readiness at `/actuator/health`, and a Grafana dashboard template. | Local verifiability is mandatory — every signal must be exercised via the Docker Compose stack (Jaeger/Prometheus/Grafana) or it is not considered delivered. |
| D-022 | Enforce quality gates in **CI/CD (GitHub Actions)** — JaCoCo ≥80% coverage + OWASP dependency-check | Manual local verification only; a different CI provider | Gate 8 requires ≥80% line coverage and zero critical/high CVEs; a `.github/workflows/ci.yml` pipeline builds, tests, enforces the JaCoCo threshold, and runs OWASP dependency-check 12.1.0. | **Open High-severity risk** — the `.github/workflows/ci.yml` workflow is scaffolded (build, test, JaCoCo threshold, and OWASP dependency-check stages are all defined) but has not yet been executed or validated on a CI runner, and the OWASP scan is as-yet-unexecuted (see the [Project Guide](project-guide.md) open-risk register). |
| D-023 | **Mask sensitive PII/PCI data (SSN and full card PAN) to the last four digits in every externally observable DTO form** — JSON serialization and the record `toString()` (explicitly logged security **deviation**) | Carry the full nine-digit `CUST-SSN` and 16-digit PAN verbatim in DTOs (literal COBOL field parity); omit the fields entirely; encrypt-at-rest only | The COBOL record layouts (`CVCUS01Y` SSN, `CVACT02Y` card number) carry the full SSN and full PAN. A Java record's compiler-generated `toString()` and Jackson's default serialization would otherwise leak that PII/cardholder data into logs and REST responses. Masking to the last four digits in the outbound/diagnostic direction — while the full value is retained in memory only where batch/statement generation genuinely needs it (for example `StatementTransactionDto.cardNumber()`) — closes the exposure without altering business behavior. Consistent with the security posture of `D-002`. | Any consumer that legitimately needs the full value must read it through an explicit internal accessor rather than the DTO's external (JSON / `toString`) form; masking is idempotent, so an already-masked value passes through unchanged. |

## Open Risks & Suggested Next Tasks

Two High-severity risks remain open at delivery; two further risks tracked here were **remediated in this checkpoint** and now carry only deployment-time residual work (the full register lives in the [Project Guide](project-guide.md)). They are recorded here because each reflects a conscious "defer" or "deliver" decision:

1. **CI/CD pipeline scaffolded but not yet validated** — a `.github/workflows/ci.yml` GitHub Actions workflow defining build, test, JaCoCo coverage, and OWASP dependency-check stages exists (`D-022`), but it has not yet been executed or verified on a CI runner; builds are still performed manually in the interim.
2. **OWASP dependency scan not yet executed** — the `dependency-check` plugin (12.1.0) is configured but the scan must be run and any critical/high CVEs remediated.
3. **Production Spring profile — delivered in this checkpoint (residual: deployment validation).** `application-prod.yml` now exists alongside `local` and `test`, with externalized DB/AWS configuration and secrets; the remaining work is validating it end-to-end against the target deployment environment.
4. **JWT signing secret — externalized in this checkpoint (residual: vault provisioning)** (see `D-009`). Base `application.yml` and `application-prod.yml` bind the secret to `${JWT_SECRET}` with no default (fail-fast; no hardcoded secret); the remaining work is provisioning `JWT_SECRET` from an environment variable or a secrets manager / vault at deploy time.

Additional upgrade considerations noted for future planning: Spring Boot 3.x→4.x (see `D-016`) and Spring Cloud AWS 3.3.0→3.4.x (see `D-017`). The full suggested-next-tasks list will be maintained in the Onboarding Guide (`onboarding.md`, forthcoming).

## Deviations & Currency Risks

Three entries are explicitly logged as deliberate departures from a literal interpretation of the requirements:

- **`D-002` — BCrypt password hashing (security deviation).** COBOL `USRSEC` stores plaintext passwords (constraint C-003). Upgrading to BCrypt is a deliberate, logged security improvement that preserves the sign-on flow while eliminating plaintext credential storage. Existing seed credentials are migrated via hash-on-first-login or a pre-hashed re-seed.
- **`D-023` — SSN/PAN masking in externally observable DTOs (security deviation).** The COBOL record layouts carry the full nine-digit SSN and 16-digit card PAN; the Java DTOs mask both to their last four digits in JSON serialization and the record `toString()`, retaining the full value in memory only where batch/statement generation requires it. This closes a PII/PCI exposure through logs and REST responses while preserving business behavior.
- **`D-016` — remaining on Spring Boot 3.x (currency risk).** The 3.5 line reached OSS end-of-life on 2026-06-30 (final OSS patch 3.5.16), and Spring Boot 4.0/4.1 now exist on Spring Framework 7. Staying on 3.x honors the explicit user mandate; the upgrade to 3.5.16 and then to 4.x is a logged next task.
