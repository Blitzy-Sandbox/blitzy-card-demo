# Decision Log

This Decision Log is the single source of truth for **why** each non-trivial choice was made while migrating the AWS CardDemo application from its legacy COBOL / CICS / VSAM / JCL mainframe stack to **Java 25 LTS + Spring Boot 3.5.16**. It fulfils the migration's **Explainability** requirement: architectural and design rationale lives here — in documentation — and never in code comments.

> **Source of truth.** The legacy COBOL programs, copybooks, and JCL jobs are the authoritative behavioral baseline for this migration. They are **not copied into this repository**; instead they are referenced by their original commit SHA **`27d6c6f`** (full `7756d895ffeb65f7ea72aaa609e356d9899afcec`). Every decision below preserves the behavior observed in that frozen source unless it is explicitly flagged as a logged deviation.

Each row records a decision, the alternatives that were weighed, the rationale for the choice, and the residual risk (with its mitigation). IDs are stable and sequential (`D-001`, `D-002`, …) so they can be cited from the [Traceability Matrix](traceability-matrix.md), the [Project Guide](project-guide.md), and code reviews. Decisions `D-001`–`D-005` are carried forward from the seed set in the [Technical Specifications](technical-specifications.md) (§0.7.3); the remainder derive from the migration's refactoring rules and the open-risk register.

| D-001 | Use `java.math.BigDecimal` for every `COMP-3` / `COMP` / `PIC S9(n)V99` financial field | `double`; `long` scaled fixed-point; scaled `BigInteger` | COBOL PIC clauses define exact decimal precision and scale; `BigDecimal` with a matching scale plus an explicit `RoundingMode.HALF_UP` applied via `setScale(...)` reproduces COBOL arithmetic identically. Zero `float`/`double` for money (Goal G2). | Boxing/allocation overhead vs. primitives — mitigated by confining `BigDecimal` strictly to monetary fields. |
| D-002 | Hash user passwords with **BCrypt** (explicitly logged security **deviation**) | Preserve plaintext (literal COBOL parity); Argon2; PBKDF2; SHA-256 | COBOL `USRSEC` stores plaintext passwords (constraint C-003). BCrypt is a well-vetted adaptive default that keeps the sign-on flow semantics intact and satisfies the "no hardcoded credentials" rule; deviating from literal parity here is a deliberate security improvement. | Existing seed passwords must be migrated via hash-on-first-login or a re-seed with pre-hashed values; minor per-login CPU cost from the BCrypt work factor. |
| D-003 | Store GDG generations as **versioned Amazon S3 objects** | Local filesystem with generation rotation; PostgreSQL large objects (LOB); EFS | GDG generation numbering and retention map natively onto S3 object versioning; batch staging uses buckets `carddemo-batch-input`, `carddemo-batch-output`, and `carddemo-statements`. | Requires LocalStack for local/test runs; S3 versioning storage cost — mitigated by lifecycle rules. |
| D-004 | Use an **SQS FIFO** queue for the CICS Transient Data Queue (TDQ) report bridge | In-memory queue; Apache Kafka; RabbitMQ; a database polling table | A CICS TDQ is point-to-point with strictly sequential reads; SQS FIFO (`carddemo-report-jobs.fifo`) preserves ordering exactly. CORPT00C's TDQ→JES bridge becomes an SQS-triggered Spring Batch launch. | SQS FIFO caps at ~300 messages/sec — comfortably sufficient for this reporting workload. |
| D-005 | Re-platform the JCL pipeline on **Spring Batch** | Custom scheduler; Quartz; Temporal; shell + cron | JCL `EXEC PGM` + `DD` + `COND` map natively to Spring Batch Job/Step beans plus `JobExecutionDecider` and `FlowBuilder`; chunk-oriented steps replace `PERFORM UNTIL END-OF-FILE` read loops. | Team learning curve for the Step/Job/Flow abstractions — mitigated by the onboarding guide. |
| D-006 | Persist VSAM KSDS data in **PostgreSQL 16 via Spring Data JPA** | MongoDB; DynamoDB; flat files; H2 | VSAM KSDS keyed access maps to `@Entity` + `JpaRepository`; AIX/PATH alternate indexes become derived queries or `@Query`; `NUMERIC(p,s)` columns preserve decimal precision and scale. | ORM impedance vs. raw VSAM performance — mitigated by the V2 index migration. |
| D-007 | Use **JPA `@Version` optimistic locking** on `Account` and `Card` | Pessimistic DB locks; no locking; application-level field compare | COACTUPC (CAUP) and COCRDUPC (CCUP) perform read-then-rewrite with change detection; `@Version` reproduces this, and an `OptimisticLockException` maps to a 409-style typed error preserving the COBOL "record changed" behavior. | Version conflicts surface as HTTP 409 — clients must retry the read-modify-write cycle. |
| D-008 | Reproduce `EXEC CICS SYNCPOINT ROLLBACK` with **`@Transactional(rollbackFor=...)`** | Manual JDBC transactions; programmatic `TransactionTemplate` | The `SYNCPOINT ROLLBACK` in COACTUPC becomes declarative rollback at the service boundary, preserving all-or-nothing multi-table semantics. | Requires correct exception typing so the declared `rollbackFor` classes actually trigger rollback. |
| D-009 | Replace CICS pseudo-conversational COMMAREA state with **stateless REST + JWT** | Server-side HTTP session; sticky sessions; a Redis session store | `RETURN TRANSID COMMAREA` cross-screen state becomes a stateless JWT bearer token, allowing horizontal scaling with no server affinity. | The JWT signing secret is externalized to `${JWT_SECRET}` (fail-fast, no default) in base and prod configuration; the residual is provisioning it from a secrets manager / vault at deploy time (see the [Project Guide](project-guide.md)). Token size vs. the compact COMMAREA. |
| D-010 | Consolidate the 17 BMS screens into **8 REST controllers** | 1:1 screen→controller (17 controllers); GraphQL; server-rendered MVC | Screens are grouped by domain — Auth, Menu, Account, Card, Transaction, User, Report, BillPayment — into cohesive JSON APIs; the target is headless (no browser UI). | The screen→endpoint mapping must be tracked precisely — captured in the [Traceability Matrix](traceability-matrix.md). |
| D-011 | Manage the schema with **Flyway migrations** (V1 schema, V2 indexes, V3 seed) | Hibernate `ddl-auto`; Liquibase; hand-run SQL | Deterministic, versioned, repeatable schema derived from the copybook record layouts and `LISTCAT`; V3 seeds from the `app/data/ASCII` fixtures. | Migration-ordering discipline is required — documented as an onboarding pitfall. |
| D-012 | Implement DFSORT/MERGE keys as **`java.util.Comparator`** chains | An external sort utility; relying on DB `ORDER BY` alone | COMBTRAN DFSORT keys become `Comparator` implementations that preserve key order, direction (ascending/descending), and duplicate handling identically. | Comparator correctness must be verified against the original sort control cards. |
| D-013 | Map `FILE STATUS` handling to **7 typed exceptions plus status enums** | Numeric return codes; a generic `Exception`; `Optional`-only signaling | Each `FILE STATUS` inspection becomes a typed exception plus a status-enum `switch`; EOF (`'10'`) is treated as normal reader termination (`Optional.empty()`/null), NOT an exception; ABEND paragraphs become runtime exceptions with structured logging. | An exhaustive status-code-to-exception mapping is required for full parity. |
| D-014 | Replace LE `CEEDAYS` date validation with **`java.time.LocalDate` + custom validators** | A legacy date library; `String` dates; `java.util.Date` | CSUTLDTC's `CEEDAYS` validation becomes `LocalDate` plus Jakarta validators, alongside NANPA phone, US state/ZIP, and FICO-range validators. | Edge-case date rules (era/Lilian boundaries) must match `CEEDAYS` exactly. |
| D-015 | Replace inter-program `CALL` linkage with **constructor dependency injection** | Static utility calls; a service locator; field injection | CBSTM03A's `CALL 'CBSTM03B'` becomes a constructor-injected `StatementFileService` bean; `USING`/`RETURNING` linkage becomes method parameters and return values. | Standard Spring idiom — no significant residual risk. |
| D-016 | **Remain on Spring Boot 3.x, upgraded to the final OSS patch 3.5.16** — a deliberate currency decision (**deviation** from the AAP's literal 3.5.11 pin) | Stay on 3.5.11; upgrade to Spring Boot 4.0/4.1 (on Spring Framework 7) | The explicit user mandate is "Spring Boot 3.x". The Spring Boot 3.5 line reached **OSS end-of-life on 2026-06-30** (final OSS patch **3.5.16**); moving 3.5.11→3.5.16 stays within the mandated 3.x line while clearing the security CVEs that Gate 8 requires (see `D-024`). | D-018 | Use **Testcontainers 2.0.3 + the LocalStack module**, with tests self-provisioning AWS resources | Mocked AWS SDK; a shared long-lived LocalStack instance; embedded fakes | The LocalStack Verification rule mandates zero live AWS; integration tests create their own S3 buckets and SQS queues in `@BeforeAll` and delete them in `@AfterAll`, never depending on pre-existing state. | Docker must be available in CI and developer environments — documented as an onboarding pitfall. |
| D-019 | Drive the migration and database seeding from the **9 ASCII fixtures** under `app/data/ASCII/` | Use the EBCDIC fixtures directly; synthesize fresh test data | The ASCII fixtures are the named validation artifacts for Gates 1 and 4 and seed the target database; the 13 EBCDIC files are reference-only, avoiding an EBCDIC→ASCII code-page conversion in the primary path. | A production EBCDIC data-migration strategy is deferred — tracked in the open-risk register. |
| D-020 | Deliver a **headless REST-only** backend with no UI and no design system | A single-page application; server-rendered pages; a component/design-system UI | The 3270 BMS screens become JSON REST endpoints; per the UI applicability assessment (§7.1) there is no browser UI, so Design System Compliance is not applicable. | Any future UI is out of scope for this migration and must be planned separately. |
| D-021 | Ship **observability from day one** — structured logging, tracing, metrics, and health | Add observability as a post-migration follow-up; logs only | The legacy system had zero observability; the target emits JSON logs (`logstash-logback-encoder` 8.0) with an MDC `correlationId`, distributed traces via Micrometer Tracing→OpenTelemetry→Jaeger, Prometheus metrics at `/actuator/prometheus`, health/readiness at `/actuator/health`, and a Grafana dashboard template. | Local verifiability is mandatory — every signal must be exercised via the Docker Compose stack (Jaeger/Prometheus/Grafana) or it is not considered delivered. |
| D-022 | Enforce quality gates in **CI/CD (GitHub Actions)** — JaCoCo ≥80% coverage + OWASP dependency-check | Manual local verification only; a different CI provider | Gate 8 requires ≥80% line coverage and zero critical/high CVEs; a `.github/workflows/ci.yml` pipeline builds, tests, enforces the JaCoCo threshold, and runs OWASP dependency-check 12.1.0. | **Open risk (CI-runner validation).** The `.github/workflows/ci.yml` workflow is defined (build, test, JaCoCo threshold, and OWASP dependency-check stages) and the OWASP dependency-check scan has been **executed locally with Gate 8 passing** (zero critical/high CVEs — see `D-024`); the remaining open item is executing and validating the full pipeline on a CI runner (see the [Project Guide](project-guide.md) open-risk register). |
| D-023 | **Mask sensitive PII/PCI data (SSN and full card PAN) to the last four digits in every externally observable DTO form** — JSON serialization and the record `toString()` (explicitly logged security **deviation**) | Carry the full nine-digit `CUST-SSN` and 16-digit PAN verbatim in DTOs (literal COBOL field parity); omit the fields entirely; encrypt-at-rest only | The COBOL record layouts (`CVCUS01Y` SSN, `CVACT02Y` card number) carry the full SSN and full PAN. A Java record's compiler-generated `toString()` and Jackson's default serialization would otherwise leak that PII/cardholder data into logs and REST responses. Masking to the last four digits in the outbound/diagnostic direction — while the full value is retained in memory only where batch/statement generation genuinely needs it (for example `StatementTransactionDto.cardNumber()`) — closes the exposure without altering business behavior. Consistent with the security posture of `D-002`. | Any consumer that legitimately needs the full value must read it through an explicit internal accessor rather than the DTO's external (JSON / `toString`) form; masking is idempotent, so an already-masked value passes through unchanged. |
| D-024 | **Security-driven dependency remediation to pass Gate 8 (OWASP dependency-check)** — upgrade Spring Boot 3.5.11→**3.5.16** and pin selected transitive dependencies; suppress documented false positives (explicitly logged **deviation** from the AAP's literal 3.5.11 pin) | Stay on 3.5.11 and accept the CVEs (fails Gate 8); suppress every finding (masks real risk); wait for BOM-managed fixes (leaves High CVEs unaddressed) | Executing `mvn -Powasp org.owasp:dependency-check-maven:check` surfaced High/Critical CVEs (CVSS ≥ 7). Four residual findings are suppressed in `dependency-check-suppressions.xml` with per-CVE justification (micrometer and httpcore false positives cross-matched to unrelated product CPEs; kotlin-stdlib whose only fix is a pre-GA build; angus-activation cross-matched to the Angus *Mail* product, which is not on the classpath). The Sonatype OSS Index analyzer is disabled (it returns HTTP 401 for anonymous requests) so the NVD database remains the authoritative, credential-free CVE source. Result: **Gate 8 passes — zero critical/high CVEs**, with no regressions (a full `mvn clean verify` stays green). | **Currency risk** persists (3.5.x is EOL — see `D-016`); the four suppressions must be re-reviewed when upstream GA fixes ship; a small number of sub-7.0 informational CVEs remain below the Gate 8 threshold and are tracked for future patch bumps. |
| D-025 | Fix the SQS FIFO report round-trip by publishing report-trigger messages through a **dedicated send-only `SqsTemplate` bean configured with `doNotSendPayloadTypeHeader()`** (QA finding **F3**) | Keep the auto-configured `SqsTemplate` (the defect); type the listener parameter as the concrete payload class so the default `JavaType` header resolves; register a custom inbound converter that ignores the header; downgrade `ReportService` to non-typed manual `sendMessage` | The auto-configured template's default converter stamps every outbound message with a `JavaType` header carrying the producer payload's fully-qualified class name (`ReportService$ReportJobMessage`). The consumer's `@SqsListener` accepts a raw `String`, so the inbound converter tries to instantiate that producer-only class for a `String` target and raises `MessageConversionException`; the report job never launches and the message redelivers until it is dropped. A dedicated `SqsTemplateConfig.sqsTemplate` bean built with `configureDefaultConverter(c -> { c.setObjectMapper(objectMapper); c.doNotSendPayloadTypeHeader(); })` omits the header so the `String` consumer converts cleanly. The bean lives in its own `@Configuration` (not `AwsConfig`) to preserve `AwsConfig`'s documented "no `@Bean`" contract and its isolation test; the auto-configuration's `@ConditionalOnMissingBean` `sqsTemplate` backs off automatically. Verified by `ReportServiceRoundTripIT` (real producer → SQS FIFO → `@SqsListener` → batch → S3, Gate 5). | The send path is now send-only and its JSON schema is stable; a future consumer wanting typed deserialization must opt in explicitly. Mitigated by the stable `ReportJobMessage` field contract and the Gate 5 round-trip test. |
| D-026 | Provision AWS runtime guarantees at startup via an idempotent **`AwsResourceProvisioner` (`@Profile("!test")`)**: enable **S3 bucket versioning** on all three batch buckets (QA finding **F1**) and create the report **dead-letter FIFO queue plus a `RedrivePolicy`** on the request queue (poison-message containment for **F3/F4**) | Enable versioning / create the DLQ only in `docker-compose` or external IaC (not guaranteed in every environment); reconcile per-job (would silently mask a bucket lost mid-run); enable versioning inside the batch writers (wrong layer, per-write cost) | GDG generations map to versioned S3 objects (`D-003`), but nothing in the batch code enabled bucket versioning, so re-runs silently overwrote prior generations (F1). Likewise the report FIFO queue had no DLQ, so a message that repeatedly failed processing redelivered forever with no containment (F3/F4). A single startup `ApplicationRunner` reconciles both concerns once and idempotently: it ensures each of `carddemo-batch-input`/`-output`/`carddemo-statements` exists and sets `Versioning=Enabled`, creates `carddemo-report-jobs-dlq.fifo`, and attaches a `deadLetterTargetArn` + `maxReceiveCount` redrive policy to `carddemo-report-jobs.fifo`. It is `@Profile("!test")` so integration tests keep self-provisioning per §0.7.7; every action is best-effort (logged, non-fatal) so an environment whose resources are managed by external IaC (app lacking create permission) still starts. It is **startup-only, never per-job**, so F4's mid-run bucket-deletion scenario still fails the job loudly. Endpoint, region, and credentials are inherited from the injected clients (LocalStack; zero live AWS). | Requires the application principal to hold S3/SQS control-plane permissions where IaC does not pre-provision; mitigated by the non-fatal best-effort design and the `carddemo.aws.provisioning.enabled` master switch (default `true`). |
| D-027 | Make batch S3 uploads **fail their step** (and fail the SQS report handler) instead of silently swallowing upload errors in `ItemStream.close()` (QA finding **F4**) — move each writer's terminal flush+upload from `close()` into `StepExecutionListener.afterStep()`, and on failure call `setStatus(BatchStatus.FAILED)` + `addFailureException(e)` + `return ExitStatus.FAILED` (**never throw** from `afterStep`); `ReportJobLauncher.onReportRequest` re-throws `FileProcessingException` when the synchronous `JobExecution` ends non-`COMPLETED`, so the `@SqsListener` does not ack and the message redelivers toward the DLQ | Keep uploads in `close()` and throw on failure (Spring Batch **swallows** both `close()` and `afterStep()` exceptions — `AbstractStep` bytecode offsets 571 and 363 — so the step still persists `COMPLETED`); **throw** from `afterStep` as the QA report suggested (also swallowed at offset 363, only logged; persisted status stays `COMPLETED`); upload per-chunk in a `ChunkListener` (fires before the terminal single-object flush, so it cannot cover the final write); add an explicit `.listener()` to each step DSL (redundant — `SimpleStepBuilder` auto-registers any writer that implements `StepExecutionListener`, bytecode offset 75) | The three batch writers (`PostTransactionItemWriter`, `StatementItemWriter`, `TransactionReportItemWriter`) buffered their output and performed the actual S3 `PutObject` inside `ItemStream.close()`. `AbstractStep.execute()` invokes both `afterStep()` (offset 346) and `close()` (offset 571) inside try blocks that catch and merely log exceptions ("Exception in afterStep callback…" offset 363), and both run **after** `upgradeStatus(COMPLETED)` at offset 198 — so an S3 failure during `close()` left the step and job persisted as `COMPLETED` and, on the report path, the SQS message acknowledged: silent data loss reported as success. The fix moves the terminal flush+upload into `afterStep()`, which runs at offset 346 **before** the status is persisted by `JobRepository.update()` at offset 492; setting `status=FAILED` there is durably persisted and returning `ExitStatus.FAILED` propagates through the `COMPLETED`-gated transitions in `config/BatchConfig` to stop the master pipeline. `close()` is reduced to buffer/temp-file cleanup only. Because the master flow reuses the same `@StepScope` step beans, the writer-level fix required **zero job-DSL changes**. For the SQS-triggered report, `ReportJobLauncher` runs on the synchronous auto-configured launcher and now re-throws when the returned `JobExecution` is non-`COMPLETED`, so the `@SqsListener` aborts without acking; the message redelivers and, after `maxReceiveCount` (`D-026`), lands on `carddemo-report-jobs-dlq.fifo`. Verified by an integration test that deletes `carddemo-batch-output` before launch (step **and** job end `FAILED`, no false `COMPLETED`) alongside a happy-path assertion (job `COMPLETED`, `tranrept.dat` present with byte-parity intact). | `afterStep` is now the durable failure boundary for batch output, so a transient S3 error fails the whole step/job rather than retrying in place — accepted because it matches the JCL abend-on-write-failure semantics and the report path is re-runnable/idempotent. Mitigated by the DLQ redrive policy (`D-026`) and `RunIdIncrementer` re-runnability. |
| D-028 | Make a POSTTRAN re-run **idempotent** with a transaction-existence guard at the top of `PostTransactionProcessor.process(...)`: if `transactionRepository.existsById(DALYTRAN-ID)` is `true` the record was posted by a prior run, so return `null` and let Spring Batch **filter** the item (not posted, not rejected, not counted) (QA finding **F2**) | Leave the blind-`ADD` posting as-is (the defect — a `RunIdIncrementer` re-run double-posts every account balance); reproduce the mainframe `TRANBKP` backup/restore + GDG rerun protection at the job level (out of scope — no GDG/dataset staging in the Java target, and it would not stop an in-process re-run); make `POSTTRAN` non-restartable / single-instance (breaks the documented re-runnability and Gate-1 replay); delete-then-repost on re-run (needlessly rewrites 262 rows and risks partial state) | Legacy `CBTRN02C` unconditionally `ADD`s each amount to `ACCT-CURR-BAL` and to the cycle credit/debit accumulators (`2800-UPDATE-ACCOUNT-REC`); the mainframe relied on the surrounding **JCL** (`TRANBKP` backup/restore of the account master plus GDG generations) to make a rerun safe. The Java target deliberately does not reproduce that dataset-staging layer (`D-003` maps GDG to S3, not to an account-master backup), so a full `RunIdIncrementer` re-execution re-posted all 262 valid records: transaction rows stayed at 262 (primary-key upsert on `TRAN-ID`) but the balance accumulators doubled (e.g. `acct_curr_cyc_credit` 1501.75 → 3003.50) and the dirtied balances shifted the reject count 38 → 113 as more records tripped the overlimit rule. The guard keys on the fact that a posted `Transaction`'s primary key **is** `DALYTRAN-ID` (`buildPostedTransaction` sets `TRAN-ID = DALYTRAN-ID`), so `existsById` precisely detects an already-posted daily row. First-run behavior is **byte-for-byte unchanged** (blind-`ADD` parity preserved for every not-yet-posted record). Re-run classification is provably **stable**: because `2800-UPDATE-ACCOUNT-REC` only ever *adds* the signed amount to the cycle credit (amount ≥ 0) or debit (amount < 0) totals, `(ACCT-CURR-CYC-CREDIT − ACCT-CURR-CYC-DEBIT)` is monotonically non-decreasing, so any record that was overlimit at its file position stays overlimit against the larger end-state balance — the 38 rejects re-reject identically and `dalyrejs.dat` remains byte-equivalent while 0 new transactions post. Verified by an integration test that runs the job twice and asserts balances identical run-once vs run-twice, 0 new posts on the second run, and a fresh single-run reject file still byte-equivalent (Gate 1). | Adds one indexed primary-key `SELECT` per daily record (negligible vs. the existing per-record XREF/ACCOUNT/TCATBAL lookups). The guard assumes `TRAN-ID` uniqueness across days (true — it is the master primary key); a genuine same-id re-submission across distinct business days would be filtered, matching the COBOL semantics where a duplicate `TRAN-ID` write is a rewrite, not a second post. |
| D-029 | Make the shared-LocalStack report FIFO queue pre-creation **idempotent and self-normalizing** across the integration suite (test-harness fix enabling the F1/F3/F4 runtime verifications to co-execute) — extract a single `AbstractBatchIntegrationTest.ensureReportRequestFifoQueue()` that creates `carddemo-report-jobs.fifo` with `ContentBasedDeduplication=true` and, if the queue already exists, forces `ContentBasedDeduplication=true` via `set-queue-attributes`; route all three per-class `@DynamicPropertySource` hooks (`ReportJobLauncherIT`, `ReportServiceRoundTripIT`, `AwsResourceProvisionerIT`) through it | Keep each hook's original hard-fail-on-nonzero-exit `create-queue` (the defect — a full-suite `mvn verify` fails at context load); set `spring.cloud.aws.sqs.queue-not-found-strategy=fail` in `application-test.yml` (breaks every non-report full-context IT, whose `@SqsListener` would then fail to resolve the queue at startup); pre-create the queue once in the shared base for *all* ITs before any listener starts (alters the `DynamicPropertiesContextCustomizer` cache-key topology and risks merging/breaking the intended per-class context isolation); stop deleting the queue in teardown (leaks messages/attributes between ITs) | The batch IT suite shares one **static** LocalStack singleton across all subclass tests in a single `mvn verify`, and `application-test.yml` deliberately sets `queue-not-found-strategy=create`. A later report IT issuing `create-queue ...ContentBasedDeduplication=true` was then rejected by SQS with `QueueAlreadyExists` ("a different value for attribute ContentBasedDeduplication"), failing its context load. The report producer path (the app's `SqsTemplate` and `ReportJobLauncherIT`'s raw `sendMessage`) supplies **no** `MessageDeduplicationId`, so the queue MUST end up CBD=true. The shared helper guarantees that end state regardless of who created the queue first: create-with-correct-attributes, else resolve the URL and `set-queue-attributes ContentBasedDeduplication=true` — a **mutable** attribute with no create/delete cooldown (`FifoQueue` is immutable but already true because the name ends `.fifo`). Verified: the previously-failing 5-class sweep (`StatementJobIT`→`ReportServiceRoundTripIT`→…) now passes 6/6; the three queue-creators pass 3/3 (with `AwsResourceProvisionerIT` still asserting the DLQ `RedrivePolicy` layered on the normalized queue); and `ReportServiceRoundTripIT` still passes alone. | Test-only change — no production code affected. Assumes `ContentBasedDeduplication` is mutable via `set-queue-attributes` (true for FIFO in both AWS and LocalStack); a future test needing per-message dedup ids would create a separate queue. Cross-context listener message-stealing was considered and empirically ruled out (the multi-IT sweep passes `ReportServiceRoundTripIT`'s full round-trip assertions). |

## Deviations & Currency Risks

Four entries are explicitly logged as deliberate departures from a literal interpretation of the requirements:

- **`D-002` — BCrypt password hashing (security deviation).** COBOL `USRSEC` stores plaintext passwords (constraint C-003). Upgrading to BCrypt is a deliberate, logged security improvement that preserves the sign-on flow while eliminating plaintext credential storage. Existing seed credentials are migrated via hash-on-first-login or a pre-hashed re-seed.
- **`D-023` — SSN/PAN masking in externally observable DTOs (security deviation).** The COBOL record layouts carry the full nine-digit SSN and 16-digit card PAN; the Java DTOs mask both to their last four digits in JSON serialization and the record `toString()`, retaining the full value in memory only where batch/statement generation requires it. This closes a PII/PCI exposure through logs and REST responses while preserving business behavior.
- **`D-016` / `D-024` — remaining on Spring Boot 3.x, upgraded to 3.5.16 (currency risk + security remediation).** The 3.5 line reached OSS end-of-life on 2026-06-30 (final OSS patch 3.5.16), and Spring Boot 4.0/4.1 now exist on Spring Framework 7. Staying on 3.x honors the explicit user mandate; the 3.5.11→3.5.16 upgrade (a deviation from the AAP's literal pin) clears the Gate 8 security CVEs (`D-024`), and the 3.x→4.x upgrade remains a logged next task.
- **`D-024` — security-driven dependency remediation (deviation from the literal 3.5.11 pin).** Passing Gate 8 (zero critical/high OWASP CVEs) required upgrading to Spring Boot 3.5.16 and pinning `tomcat` 10.1.56, `netty` 4.2.16.Final, `log4j2` 2.25.5, and `opentelemetry-semconv` 1.43.0, plus four documented, per-CVE-justified suppressions of false positives / no-GA-fix residuals. NVD is the authoritative CVE source (the OSS Index analyzer is disabled for anonymous access).
