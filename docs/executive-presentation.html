1. Business context and the objective

CardDemo is a credit card management application. It maintains accounts, cards and customers, records transactions, posts them daily, calculates monthly interest, produces statements and prints reports. It was implemented in IBM Enterprise COBOL and runs under CICS for its online screens, VSAM for its data, JCL for its batch stream and BMS for its 3270 terminal maps, on z/OS. The complete source of record is in this repository under app/.

The constraint is the substrate, not the business logic. The rules encoded in these programs are correct, in production use, and were the product of years of refinement. What limits the application is the platform underneath it: a terminal protocol, a record-oriented file system, a job scheduler and a transaction monitor that together determine how the software can be staffed, tested, deployed and integrated. The objective is therefore stated narrowly and deliberately: replace the execution substrate while reproducing the behaviour exactly.

The acceptance contract

Behavioural parity across all twenty-two catalogued features, F-001 through F-022, is the acceptance contract — not an aspiration. The practical consequence is unintuitive and is worth stating plainly to anyone reviewing this programme: known legacy quirks are preserved and documented, never corrected. Where a program does something odd, the Java code does the same odd thing, cites the source line that made it do so, and records the decision. A migration that quietly improved behaviour would be impossible to verify, because the only available oracle for “correct” is the legacy system itself.

Separately from parity, three things the legacy system does not have are added, because a modern substrate is not usable without them: an observability layer, an automated regression net, and a reproducible build. These are additions, and they are labelled as additions rather than presented as equivalence.

How the 28 programs divide

The corpus is 17 online transaction programs, 10 batch programs and 1 statically called date utility [app/cbl/]. The largest single program is the account update program COACTUPC at 4,236 lines; the sign-on program COSGN00C is 260 lines [app/cbl/COACTUPC.cbl, app/cbl/COSGN00C.cbl]. Two of the batch programs, CBSTM03A.CBL and CBSTM03B.CBL, carry an uppercase file extension, so a naive case-sensitive scan for *.cbl silently omits them and under-reports the corpus by 1,154 lines — a small detail with a real consequence, since one of those two programs is the sole source for statement generation. The same trap exists in the job control directory, where CREASTMT.JCL is the one member of 29 with an uppercase extension. Both were caught by matching case-insensitively; both are the reason the counts above are 28 and 29 rather than 26 and 28.

The data estate

The catalogue listing records, in its own summary of entries processed, 10 base VSAM clusters, 3 alternate indexes, 3 access paths and 7 generation data groups [app/catlg/LISTCAT.txt, summary block L3936-L3950]. Each of those figures matters to the target design: every cluster becomes a table, every alternate index becomes an indexed query, and every generation data group becomes an object-storage prefix. Under-counting any of them removes a required artefact from the plan, so the summary block is quoted rather than inferred.

The screen estate, and a scope-integrity finding

The 17 generated symbolic maps declare 441 input fields in total [app/cpy-bms/]. Those fields are the field contract: each one fixes a name, a type and a length that the corresponding Java request or response object must reproduce, because silent truncation or widening would break parity in a way no test catches unless the contract is asserted.

The count of externally reachable operations required a judgement, and it is published here rather than buried. The CICS resource definitions declare 18 transactions and 18 programs, but only 17 mapsets [app/csd/CARDDEMO.CSD]. The eighteenth transaction-and-program pair points at a program named in the definitions and nowhere else: it has no source file anywhere in the repository, its only two occurrences being the two definition lines themselves [app/csd/CARDDEMO.CSD:L211, :L390]. The corroborating inventory in the repository readme lists exactly 17 online entries, under its #### **Online** heading.

Scope integrity: 17 operations, not 18

The programme declined to invent an endpoint for a program that does not exist. A dangling definition with no code behind it cannot be migrated, so it is documented as a dangling legacy definition and carried forward as a finding. The target therefore exposes 17 REST operations. Reporting 18 would have inflated the delivery on paper while leaving one of them unimplementable.

What is deliberately untouched

app/ remains frozen and byte for byte unchanged, and it holds three roles simultaneously that it loses the moment it is edited. It is the parity oracle that target output is compared against; it is the field-contract source from which every type, length and precision is derived; and it is the traceability anchor that the paragraph-level mapping cites by line. The migration is consequently purely additive and stays in this repository: the Java tree at src/ sits beside the frozen tree, sharing its history and its licence.

4. Before and after, side by side

Before, in words

3270 terminals drive a CICS region. The region holds each conversation's state in a communication area and moves between screens by transferring control from one program to another, rendering 17 BMS mapsets whose generated symbolic maps declare 441 input fields [app/bms/, app/cpy-bms/]. Behind the screens sit 28 COBOL programs, which read and write 10 VSAM key-sequenced clusters reached through 3 alternate indexes and 3 access paths [app/catlg/LISTCAT.txt, summary block L3936-L3950]. The online and batch worlds are joined by one closed loop: the report screen writes an 80-byte job deck to a transient data queue named JOBS [app/csd/CARDDEMO.CSD:L499], the JES2 internal reader consumes that deck, and JES2 then executes 29 job control members with sort and dataset utilities, producing 7 generation data groups and running the very same COBOL programs. Two facts about this picture matter more than the boxes: session state lives in the communication area rather than in the client, and there is no observability tier at all — no metrics, no tracing and no structured logs, only printed lines in the job log.

After, in words

An HTTP client sends and receives JSON. Each request passes through a filter that assigns a correlation identifier, then a filter that validates a signed token, then role-based authorisation, before reaching one of 8 controller classes that expose 17 operations. Controllers delegate to 21 service beans, which are organised so that each private method corresponds to one paragraph of the COBOL program it replaces. The beans reach data through 11 repositories onto PostgreSQL 16, whose schema is 11 tables, 3 B-tree indexes standing in for the 3 alternate indexes, and 3 ordered migrations. The batch stream becomes 6 jobs, in which a decider replaces the job control return-code gating and a parallel split models the statement and report branches that have no ordering dependency between them; those jobs call the same service beans the online operations call, which is what keeps one set of business rules rather than two. Object storage replaces the generation data groups, a first-in-first-out queue replaces the transient data queue and triggers the batch jobs in place of the internal reader, and a notification topic replaces operator notification — all three against a local emulator with zero live cloud credentials. Across every layer, traces, metrics, structured logs and health checks are emitted, which is new capability rather than a translation of anything.

All 28 programs are accounted for. Three of them required a decision that could reasonably have gone the other way, and publishing those decisions is the point of this subsection: they are precisely the cases a superficial migration drops without anyone noticing.

A batch program with no distinct target job.

A job with no COBOL program.

6. Why exact reproduction is hard

Reproducing behaviour exactly is harder than rewriting it, and the difficulty is concentrated in a small number of places. Five are described below in plain terms, because each one is a place where the obvious modern implementation produces working software that behaves differently from the original.

6.1 Money must be decimal, not floating point

Amounts and rates are held as exact decimal values whose number of decimal places is taken from each field's original definition, and stored in columns declared with that same precision. No floating-point type appears in any financial field, because binary floating point cannot represent ordinary decimal amounts exactly and its errors accumulate over a batch run.

Formulas are also transcribed in their original shape rather than in an algebraically equivalent one. Monthly interest, for instance, is computed by multiplying the balance by the rate and then dividing by 1200 in a single step [app/cbl/CBACT04C.cbl:L462-L470]. Dividing by 100 and then by 12, which is mathematically identical, rounds differently at the intermediate step and produces a different figure on some inputs. Parity therefore constrains not just the answer but the order of operations.

6.2 Signs are hidden in the last character of a number

The legacy data files encode whether a number is positive or negative in the final character of the field, a technique known as overpunch: the digit and the sign share one byte, so an amount can end in a brace or a letter rather than a digit. Evidence sits in the first line of the account fixture, where three money fields each end in a brace [app/data/ASCII/acctdata.txt:L1], and in the category balance and disclosure group fixtures [app/data/ASCII/tcatbal.txt:L1, app/data/ASCII/discgrp.txt:L18].

The trap is that the very same letters occur legitimately inside text fields such as merchant names. Decoding therefore has to be position-aware — driven by each field's declared definition, never by searching for characters — or ordinary words get silently reinterpreted as negative numbers. The daily transaction fixture contains both positive and negative sign characters across its 300 records [app/data/ASCII/dailytran.txt], so it genuinely exercises the negative-amount path and must not be normalised before use.

6.3 Quirks are reproduced, not repaired

Where the legacy system does something odd, the Java system does the same odd thing and records why. Two illustrations make the principle concrete.

First, two validation checks run one after another with nothing between them, so when both fail the second rejection reason overwrites the first and a single rejected record is written carrying only the later reason [app/cbl/CBTRN02C.cbl:L393-L422]. An implementation that guarded the second check, or that emitted two rejections, would be more defensible in isolation and would diverge from the system of record.

Second, a batch report starts a new total whenever the card number changes [app/cbl/CBTRN03C.cbl:L181-L184], while the label printed on that total line reads “Account Total” [app/cpy/CVTRA07Y.cpy:L58]. Both the grouping and the wording are preserved exactly as they are. Correcting either one changes output that the parity comparison is measured against.

6.4 Detecting a concurrent edit needs two mechanisms, not one

Before writing an account change, the legacy screen compared the values the user had been shown against the values currently on file, field by field, and abandoned the write if anything had moved [app/cbl/COACTUPC.cbl:L4109-L4193]. That is a stronger and stranger guarantee than it first appears: it detects which values differ and in what representation, not merely that the record changed.

Because the new interface is stateless, there is no server-side screen to hold that comparison snapshot between requests, so the snapshot travels with the request. And two layers of protection are used together: a database version check, which catches any concurrent write, and an explicit field-by-field comparison, which reproduces the original decision. Neither alone is sufficient — a version check would reject a concurrent write that restored a field to the value the user was shown, which the legacy system accepts.

6.5 Atomicity, and why one deployable unit was mandatory

The clearest architectural message in this document

The target is one deployable application — a modular monolith — and explicitly not a set of microservices. This is the decision most likely to be questioned, so the reason is stated in full rather than asserted.

An account update writes to two datasets inside one indivisible step [app/cbl/COACTUPC.cbl:L3888-L4105], and daily posting writes to three [app/cbl/CBTRN02C.cbl:L424-L444]. Either all of the writes in each group take effect or none of them does. Splitting those writes across independently deployed services would forfeit that guarantee and force compensating transactions in its place, which do not fail the same way: there is a window in which the data is half updated, and the recovery path is new code with new failure modes of its own.

That is a behaviour change, and behaviour change is precisely what this programme forbids. Modularity is therefore delivered inside one deployable unit — separated packages, one service bean per program, clear layering — which buys the maintainability benefit without spending the atomicity guarantee. The reasoning is developed at length in architecture-before-after.md.

7. Security and observability

7.1 Security

The legacy system stored and compared passwords as plain text. The seed records that populate its user file are ten fixed rows carried inline in a job control member, and every one of them carries the same literal plain-text password [app/jcl/DUSRSECJ.jcl:L35-L44]. That value is deliberately not reproduced anywhere in this document; it is referred to by locator only. The migration stores those users as BCrypt cost-10 hashes rather than as plain text, which protects the stored representation — it does not change the credential a caller presents, and it does not render that credential unusable. These are therefore public demo-only credentials: they are published in the frozen corpus and in README.md, so they must be assumed known to everyone. What contains them is the deployment profile, not the hashing: the demo users are seeded only under the isolated local and test profiles and are absent from the production profile, where seeding them is forbidden.

The measures below are properties of the implementation, each backed by a named artefact.

Password hashing.
Passwords are stored as BCrypt hashes at strength 10, replacing the plain-text comparison the source performs. The seeded users are written as hashes by the seed migration, never as the literal.
No committed signing key.
The token signing key is resolved from an environment variable in every profile, with no committed default and fail-fast behaviour on absence: an unset variable aborts start-up rather than silently falling back to something guessable.
Least privilege.
Administration routes are restricted to the administrator role, and a dedicated production profile externalises every secret rather than shipping development conveniences into a deployment.
Log masking.
Credentials, password hashes and social security numbers are masked in log output. This matters concretely because the customer record layout carries a nine-digit social security number and the user layout carries a password field, so unmasked logging would leak both.
Dependency discipline.
Every dependency and build plugin is pinned to an exact version, with no ranges and no floating selectors, and an automated vulnerability scan is bound into the build so the pinning is verifiable rather than merely asserted.
No live cloud credentials.
All cloud interaction targets a local emulator. No code path reaches a live provider endpoint and no credential material appears in any file.

Two defects recorded against the prior attempt at this migration are closed by the current work: a hardcoded signing key and the absence of a production profile, both classified High [docs/project-guide.md:L51-L52]. Each is now addressed by a named file; see section 10.

7.2 Observability

The starting point is worth stating bluntly: the legacy corpus contains no instrumentation at all. Its entire diagnostic surface is print statements to the job log, plus one routine that formats a file status code into four characters for display. There are no metrics, no traces, no structured records and no health check anywhere in 19,254 lines.

Four capabilities are added, and they are shipped with the initial implementation rather than deferred to later work:

  • Structured logging. Log records are emitted as machine-parsable JSON carrying a trace identifier, a span identifier and a correlation identifier, so a single request or batch run can be followed end to end.
  • Distributed tracing. Trace context is propagated across the application, including onto outbound calls, and exported to a trace collector.
  • Metrics. A metrics endpoint publishes four named counters: records processed, records rejected tagged by reason, authentication attempts, and total transaction amount. The tag on the rejection counter is what turns the legacy end-of-run printed totals into a signal an operator can act on.
  • Health. A composite health endpoint covers the database, object storage and the queue, with separate liveness and readiness groupings.

No throughput, latency or utilisation figure is stated in this document, for either system. The legacy application publishes no service-level objective, and no measurement of the target has been captured as published evidence — see section 8, gate 3.

9. Decisions, substitutions and disclosed deviations

9.1 Mechanism substitutions

9.2 Three disclosed deviations

A deviation is different, and the distinction is the most important one in this section: the Java system deliberately behaves differently from the source, and the difference is disclosed rather than absorbed. Three are highlighted here because a stakeholder should know about them. They are improvements, not parity, and they are labelled that way in the register. The complete set of labelled deviations is recorded in DECISION_LOG.md and in the register in validation-gates.md; this is a selection, not the whole list.

Table 7. Three disclosed deviations a stakeholder should know about.
Deviation What the legacy system does What the target does, and why it is disclosed
One transaction boundary closes an orphaned-write hazard Daily posting performs its three writes as three independent commits, so a failure part-way through can leave two rows written and the third not [app/cbl/CBTRN02C.cbl:L424-L444] The three writes become one indivisible unit, so the hazard cannot occur. This is strictly better than the source, which is exactly why it is labelled a deviation instead of being presented as equivalence
A hard capacity ceiling is removed Statement generation holds its working set in a fixed table of 51 card entries each holding 10 transactions — a hard ceiling of 510 transactions per run — and increments its indexes with no bounds check at all [app/cbl/CBSTM03A.CBL:L226, :L228, :L232] The target streams instead, so there is no ceiling and no silent overrun. 9.3 Legacy defects logged rather than fixed

Several genuine defects exist in the legacy job control and programs — a corrupted dataset statement, a record-length mismatch between two steps of the same job, a procedure whose internal name differs from the member name that invokes it, a misspelled job name, and a rejection code that is assigned on a path where it can never be reported. None is repaired.

The reason is the same one that governs the preserved quirks in section 6: repairing them would change behaviour that the parity comparison is measured against, and the comparison is the only means of proving the migration correct. Each is recorded with its locator in the register in validation-gates.md, so that a later programme can decide to fix them deliberately, with parity re-baselined, rather than inheriting them unknowingly.

11. Current position, risks and next actions

This section is deliberately the least flattering one in the document. A stakeholder reading a modernisation summary is entitled to know what has not been established, and an unqualified claim here would be the easiest thing in the programme to disprove.

11.1 What is not established

No gate result is recorded in this document.
Every entry in table 4 reads Not available. Design, however thorough, is never a pass. The standing of each gate is maintained in validation-gates.md and should be read there.
No capture from the real legacy runtime exists.
The gap is narrow, and stating it more widely — that “no expected legacy baseline output artefact exists in the repository”, so parity “cannot yet be executed as a true diff” — would overstate it in both halves. End-to-end parity is executed as a true byte-level diff against two independent expectations held in the repository: the frozen program's own output, produced by compiling app/cbl/CBTRN02C.cbl unmodified and running it against the frozen fixtures, and a second expectation re-derived from the same source by a harness that imports no production type. What is absent is narrower: a capture from the real runtime — the frozen COBOL executed on z/OS or a licensed emulator, which would corroborate both expectations rather than replace either. That capture cannot be produced from inside this repository.
Documentation publication has a failure path that is silent by default.
A page absent from the site navigation never appears in the published site, and on a default MkDocs configuration nothing reports a problem — the omission is reported at INFO level, so no error and no warning a strict build could fail on. See finding H-5 in section 10. mkdocs.yml sets validation.nav.omitted_files: warn, so a strict build does fail on it here; the filename must still match the navigation entry exactly, which the build cannot check.

11.2 The environment position

The state of the authoring host decides which gates can run at all, so it is published rather than assumed, as a dated reading in [validation-gates.md]. That reading records a container runtime that is available — Docker Engine with Compose and a reachable daemon — together with a host Java runtime and compiler, Maven, the cloud emulator, the cloud command-line client and the documentation site generator, whose strict build was then actually run and its outcome recorded. The figures are not restated here; the ledger is the authoritative record and is the only place they are maintained. The container runtime is not unavailable, and no gate may be reported blocked on that basis.

11.3 A Blocker-severity build finding, already remediated in the plan

One finding is severe enough to stop a build outright and is recorded as Blocker (B-1 in section 10). In stakeholder terms: a third-party test library renamed its components at a major version, and the surrounding framework independently pins an older version of the same library. Two corrections are needed and they only work together — either one applied alone still fails. It was found before it could break anything, because every dependency was verified against the public package registry rather than assumed, and the remediation is written into the plan. The coordinate-level detail is in technical-specifications.md.

11.4 Deferred hardening, disclosed as residual risk

Eight items are knowingly out of scope. They are disclosed rather than dropped, each with the trigger that would bring it into scope, in the register in validation-gates.md: table partitioning; read replicas; connection-pool tuning; transport-layer security termination; request rate limiting; URI-based API versioning; generated API specification tooling; and encryption at rest for personally identifiable data. Two of those — transport security and encryption at rest — are deployment decisions rather than application defects, and both must be settled before any exposure beyond a local environment.

11.5 On the prior attempt's numbers

project-guide.md is retained unchanged as prior-run evidence, because deleting it would erase the record of what a previous attempt reported. Its completion, hours, test-count, coverage and gate-pass claims are not evidence for the current implementation, and none of them is restated or endorsed anywhere in this document. It is cited here for exactly one purpose: as the record of the four defects the current work closes (see H-1, H-2 and H-3 in section 10).

For the same reason, this document states no completion percentage, no effort figure, no test count, no coverage measurement, no throughput or latency figure and no financial or business-benefit quantification. Where such a figure has been measured it is maintained in validation-gates.md and read there; restating one here would create a second copy that goes stale silently, and publishing an unsupported figure in a stakeholder summary is the most damaging thing this page could do.

11.6 Next actions, in order

  1. Obtain a capture from the real legacy runtime, or formally agree that the two committed expectations are the accepted oracle. That capture is the one piece of gate 1 evidence this repository cannot produce.
  2. Keep the compose topology bring-up current as the topology changes. The bring-up that was once the outstanding half of gate 8 has been produced, against the seven-service topology the stack now declares, all seven containers healthy with a second up converging in 1.11 seconds. What remains is upkeep rather than absence: a service count is evidence that expires whenever the topology is changed.
  3. Keep the host toolchain provisioned so that build and documentation verification remain reproducible rather than dependent on one machine's state.
  4. Publish each new evidence artefact and update the ledger, closing every remaining absence by producing the artefact a reviewer would open — never by rewording the result.
